Section 01 — Overview

What this system does

Before this system existed, someone at Trakop had to manually check every enquiry form — look up who the company is, judge their size, decide if they are a real prospect — and then write a summary to pass to the sales team. That process was slow, inconsistent, and easy to miss.

This system automates the entire thing. The moment a prospect anywhere in the world submits the form, an AI agent wakes up, validates the lead, researches the company on the internet, scores how good a fit they are, and sends the sales team a complete, ready-to-act briefing on Telegram. Zero human involvement. Done in about three minutes.

One-sentence summary A prospect fills the form → the system automatically validates, researches, scores, and delivers a lead report to the sales team on Telegram.
Fig 1.1 — Five steps from form submission to sales team notification

Who uses this system

Sales team

Receive ready-to-act briefings

Gets a Telegram message for every lead. No manual lookup needed. The message includes the company's website, key contacts, ICP score, recommended action, and a personalised icebreaker for the first call.

Prospects

Fill the enquiry form

Visit the form (hosted on GitHub Pages, accessible anywhere), fill in their details and business requirements, and submit. They see a confirmation immediately. The pipeline runs silently in the background.

Section 02 — Architecture

How the system is built — old vs new

The system started as a fully local setup — everything ran on one Mac Mini and could only be tested from that machine. It has now evolved so that anyone on the internet can submit the form, and the pipeline runs automatically. Here is what changed and why.

Before — Local only (v1)
📄HTML form served from Mac Mini, only accessible at localhost
🔒Nothing on the internet could reach it
🖥️Had to be tested sitting at the Mac Mini
⚡server.js on port 8080 → OpenClaw port 18789
❌Real HubSpot integration impossible
Now — Internet accessible (v2)
🌐Form hosted on GitHub Pages — public URL, works on any device
🚇Cloudflare Tunnel bridges internet → Mac Mini securely
📱Can be tested from phone, another laptop, anywhere
⚡Same server.js and OpenClaw — zero changes to pipeline
✅Ready to connect real HubSpot workflow

The complete architecture — every component in one picture

Fig 2.1 — Full architecture. Left side = public internet. Bottom green zone = Mac Mini (private, never exposed directly).
Key design principle — the Mac Mini is never directly exposed The Cloudflare Tunnel is a one-way pipe. It lets traffic in from the internet, but the Mac Mini never "opens a port" to the outside world. Think of it like a secure post box — people can drop letters in, but no one from the street can reach inside.

Why server.js stays in the chain — the proxy pattern

A natural question is: why not have the form talk directly to OpenClaw? Why have a middleman? Four strong reasons:

Security

OpenClaw stays hidden

server.js is what the internet can reach (via Cloudflare). OpenClaw never directly handles an external request. If someone tries to attack or abuse the endpoint, they hit server.js — a simple Node.js script — not the AI engine.

Compatibility

Field name translation

HubSpot sends data with field names like firstname, but the pipeline expects first_name. server.js translates between the two. Switch form tools in future? Change one place in server.js. Everything else is untouched.

Control

Format normalisation

OpenClaw expects the payload wrapped as {"body": {...}}. server.js does this wrapping. The form does not need to know about OpenClaw's internal format — it just sends plain form data.

Future-proofing

Rate limiting ready

Need to add rate limiting, request logging, or field sanitisation later? One place: server.js. The pipeline, OpenClaw, and the database never need to change. All protection upgrades happen at the gate.

Section 05 — The AI pipeline

The 4 stages — what the AI actually does

Once the data reaches OpenClaw, an AI agent reads the pipeline instructions (LEAD_PIPELINE.md) and runs four stages in sequence. Each stage can stop the pipeline early — this saves time and avoids wasting AI API calls on junk leads. The sales team is notified via Telegram regardless of which stage stops it.

Fig 5.1 — Pipeline flow. Each stage can trigger an early stop. The red dashed paths always end with a Telegram notification.
Stage 1 — Validate

Is this a real, clean lead?

  • Checks required fields are present (name, email, business type, requirements)
  • Spam detection: gibberish text, disposable email domains, nonsense requirements
  • Duplicate check: has this email or company submitted before?
  • Competitor check: is the email domain from a known competitor?
  • If any check fails → Telegram alert with reason, pipeline stops
Stage 2 — ICP Scoring

How good a fit are they?

  • Business type fit: does their category match a Trakop product?
  • Company size: individual, small (1–50), mid (50–500), enterprise (500+)
  • Solution need: do their requirements actually describe needing delivery software?
  • Order volume: orders/day and customers served signal their scale
  • Score under 30 → rejected, Telegram alert, pipeline stops
Stage 3 + 3b — Research

What does the web say about them?

  • Runs up to 4 targeted web searches (company + business type, LinkedIn, revenue signals)
  • Finds: website, LinkedIn, key contacts, employee count, tech stack, recent news
  • Stage 3b cross-checks: does research confirm what the form said?
  • ICP score revised up or down based on findings
  • If research reveals competitor or score drops below 30 → stop
Stage 4 — Deliver

Send the briefing to sales

  • Compiles everything into a structured Telegram message
  • Includes: lead ID, ICP score, company research, website, LinkedIn
  • Adds: icebreaker, hypothesised pain point, pitch strategy
  • Recommended action: call immediately / reach out today / low priority
  • Updates database: telegram_sent = true, status = notified

ICP scoring — how the 0–100 score works

ICP stands for Ideal Customer Profile. The score represents how closely this lead matches the type of business Trakop is built for. It is calculated twice: once from form data alone in Stage 2, then revised after web research in Stage 3b.

80–100 🔥 Hot Strong fit, clear need, ready to buy. Call immediately.
50–79 🌡 Warm Decent fit, some open questions. Reach out today.
30–49 ❄ Cold Weak fit, unlikely to convert. Low priority follow-up.
0–29 ✖ Rejected Poor fit. Pipeline stops here. No follow-up needed.
Important — the score is calculated twice The Stage 2 score is preliminary — based only on what the prospect wrote in the form. After Stage 3 research, the score can increase by up to 10 points if research confirms good fit, or decrease significantly if research reveals mismatches (e.g. the company is actually an enterprise too large for Trakop's sweet spot, or they are a delivery software competitor themselves).
Section 06 — Security

How everything is protected

Even though the system now accepts submissions from anyone on the internet, multiple independent layers of protection prevent abuse, unauthorised access, and data leakage. Each layer works independently — so if one were somehow bypassed, the others still hold.

Fig 6.1 — Four independent security layers. The innermost components are physically unreachable from the internet.
Layer 1 — Cloudflare

HTTPS encryption + DDoS protection

All traffic between the prospect's browser and the Mac Mini is encrypted end-to-end. Cloudflare also absorbs denial-of-service attacks — a flood of fake requests gets stopped at Cloudflare's network before it reaches the Mac Mini.

Layer 2 — Secret token (server.js)

Every request must carry the password

server.js checks the Authorization header on every request. If it does not contain the exact WEBHOOK_SECRET value from your .env file, the request is rejected with a 401 error instantly. OpenClaw never sees it.

Layer 3 — OpenClaw auth

Second token check

Even though server.js already verified the token, OpenClaw checks it again independently. A request that somehow slipped past server.js would still fail here. Two independent checkpoints for the same credential.

Layer 4 — Loopback binding

Core services are physically unreachable

OpenClaw and the database are bound to 127.0.0.1 (the machine's own loopback address). Even if every other security layer failed, these services cannot receive traffic from outside the Mac Mini — not from the local network, not from the internet.

Pipeline — Stage 1

Spam, duplicate, and competitor blocking

The pipeline itself acts as another filter. Every submission is checked against known competitor domains, spam patterns, and duplicate submissions. Anything suspicious is logged and rejected before the expensive web research stage runs.

Data storage

Everything stays on the Mac Mini

All lead data is stored in a local SQLite file. Nothing is sent to a third-party database or cloud storage. The only data that leaves the Mac Mini is the formatted Telegram message — and that contains only the briefing, not raw database records.

The most important credential — WEBHOOK_SECRET The secret in your .env file is the single key that protects the entire endpoint. Keep it out of version control (your .gitignore should exclude .env — verify this). If it is ever exposed or committed to GitHub, generate a new one immediately and update it in both .env and the GitHub Pages form's JavaScript config (TUNNEL_URL header is sent automatically — the secret is what OpenClaw validates).

What an attacker would face

If someone discovered the tunnel URL and tried to abuse it, here is what they would encounter:

  • 1

    They send a POST request to the tunnel URL

    Cloudflare receives it over HTTPS. No issue yet for the attacker.

  • 2

    server.js checks the Authorization header

    No valid token → immediate 401 rejection. The request never reaches OpenClaw. Pipeline is never touched.

  • ✓

    Attack stopped at Layer 2

    Without knowing the exact WEBHOOK_SECRET, an attacker can do nothing. The token is a long random string — not guessable by brute force in any reasonable time.

System reliability — honest assessment

Strong ✅

Pipeline logic and error handling

The 4-stage structure is well-designed. Early exits prevent wasted AI calls. The sales team is always notified, even for junk. Isolated sessions mean one slow lead cannot block others.

Strong ✅

Complete audit trail

Every action at every stage is logged to pipeline_log in the database. You can always look up exactly what happened to any lead — what stage it reached, what decision was made, why.

Watch this ⚠

Mac Mini uptime dependency

The whole system runs locally. If the Mac Mini sleeps, loses power, or loses internet, submissions fail. Set System Settings → Energy Saver → Never sleep. Consider a UPS (battery backup) for the Mac Mini.

Watch this ⚠

z.ai API dependency

The AI model is called via the z.ai API. If that service is down or rate-limited, agent sessions will fail. Test what the pipeline does in this scenario and whether OpenClaw retries automatically.

Before going to production — hardening checklist Run openclaw doctor --repair (fixes nvm warning). Set up server.js with PM2 (auto-restart). Set Mac Mini to never sleep. Set up a permanent named Cloudflare tunnel (stable URL). Run a full end-to-end test after every configuration change. Monitor the log file weekly: /tmp/openclaw/openclaw-*.log.
